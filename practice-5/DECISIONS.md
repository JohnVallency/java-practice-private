# DECISIONS.md

## Вариант

Номер варианта: 27.

Часть А: `parseHours` принимает `-1` как отгул.

Метод `overtimeDays` не считает отгулы переработкой.

Метод `average` делит сумму рабочих часов на количество неотгульных дней.

Часть Б: `addDayOffCount(int[] hours) → int` возвращает количество отгулов.

## Решение 1

### Формулировка

Маркер `-1` разрешён только как отдельное точное значение.

Остальные отрицательные числа запрещены.

Для проверки используется выражение `^(-1|0|[1-9][0-9]*)$`.

После проверки формата значение проверяется по диапазону от `-1` до `16`.

### Альтернатива

Можно было разрешить любое число со знаком, а затем проверять диапазон.

### Обоснование

Выбранный вариант сохраняет исходное требование о запрете знака для рабочих часов.

Исключение сделано только для предусмотренного вариантом маркера отгула.

Так значения `-2`, `+8`, `08` и `8.0` остаются ошибочными.

## Решение 2

### Формулировка

Отгул не является отрицательным количеством рабочих часов.

Поэтому `total` исключает `-1` из суммы.

Метод `average` делит эту сумму на число дней, значение которых не равно `-1`.

Если все пять дней являются отгулами, среднее равно `0.0`.

`weeklyOvertime` использует результат `total`, поэтому маркеры не уменьшают сумму часов.

### Альтернатива

Можно было включать `-1` в сумму как обычное отрицательное число.

### Обоснование

Такой вариант искажал бы сумму, среднее и недельную переработку.

Выбранное поведение соответствует смыслу отгула и согласовано для всех метрик.

## Ответы на вопросы методички

### Вопрос 1

Наиболее вероятную ошибку входных данных предотвращает проверка количества элементов после
`split(";", -1)` в методе `parseHours` класса `TimesheetAnalyzer`.
Пользователь может пропустить один день, добавить лишнюю точку с запятой или оставить
разделитель в конце строки.
Аргумент `-1` сохраняет последнее пустое поле, поэтому завершающий разделитель также
обнаруживается.
Если элементов не пять, метод сразу выбрасывает `IllegalArgumentException` с описанием
структуры и фактическим количеством значений.
Такая fail-fast проверка выполняется до преобразования чисел и не позволяет программе
обрабатывать неполную или сдвинутую неделю.

### Вопрос 2

Ключевые правила находятся в классе `TimesheetAnalyzer`, потому что этот класс содержит
бизнес-логику и не выполняет ввод или вывод.
Для варианта 27 особенно важны методы `parseHours`, `average` и `addDayOffCount`.
Первый разрешает только специальное значение `-1`, второй исключает отгулы из делителя,
а третий подсчитывает их количество.
Размещение правил в отдельных статических методах позволяет проверять каждое поведение
независимо через `SelfCheck`.
Интерактивный режим и чтение CSV только вызывают эти методы, поэтому один и тот же алгоритм
используется при автоматической проверке и при вводе преподавателя.

### Вопрос 3

Блок Activity-диаграммы «Для каждого элемента» соответствует циклу `for` в методе
`TimesheetAnalyzer.parseHours`.
На каждой итерации код проверяет формат строки, разрешая `-1` или целое число без ведущих
нулей, преобразует значение в `int` и контролирует диапазон от `-1` до `16`.
Если проверка не проходит, поток переходит к формированию сообщения об ошибке и завершается.
Если все пять элементов корректны, диаграмма ведёт к вычислению показателей.
Таким образом, один блок показывает логически завершённый цикл, не копируя каждый оператор
Java в отдельный узел.

### Вопрос 4

Изменение дневного порога переработки с восьми часов на другое значение должно затронуть
только константу `DAILY_NORMAL_HOURS` класса `TimesheetAnalyzer`.
Метод `overtimeDays` сравнивает каждый рабочий день с этой константой, а остальные классы
не содержат копий порога.
При таком изменении потребуется обновить ожидаемые результаты связанных проверок, но сама
структура программы и алгоритм разбора строки сохранятся.
Локализация правила уменьшает риск случайно получить разные пороги в интерактивном режиме,
unit-проверках и data-driven проверках, потому что все режимы вызывают один метод бизнес-логики.

## Фрагмент кода для анализа

В условии `i <= hours.length` допущена ошибка на единицу: при `i == hours.length` код обращается
за последней допустимой границей массива и получает `ArrayIndexOutOfBoundsException`.
Причина в том, что индексы массива начинаются с нуля и заканчиваются значением
`hours.length - 1`, поэтому правильное условие имеет вид `i < hours.length`.
После проверки R1 массив содержит ровно пять значений, а исправленный цикл безопасно
обрабатывает их все без падения.
